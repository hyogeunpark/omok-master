# 003 — 온라인 랭킹(리더보드): 유예 (사용자 확보 후 재검토)

- **상태**: 유예 — 도입하지 않음. 사용자 기반이 형성된 뒤 재검토.
- **결정일**: 2026-07-27
- **관련**: [001-cloud-sync-firebase.md](001-cloud-sync-firebase.md), [../spec/streak.md](../spec/streak.md), [../index.md](../index.md) §6

## 배경

스트릭(출석·연승) 도입으로 진행감을 만들면서 **"다른 사람과 순위를 비교할 수 있는가"**가 논점이 되었다. 현재 모든 기록은 기기 로컬(`localStorage`)에만 있고, 서버 기반 랭킹은 `docs/index.md` §6에서 범위 밖으로 규정되어 있다.

## 결정

**지금은 온라인 랭킹을 도입하지 않는다.** 다음 세 가지 이유 때문이다.

### 1. 검증 불가능한 점수 (가장 큰 문제)

게임 로직이 전부 클라이언트에서 실행된다. 사용자가 `localStorage`나 네트워크 요청을 조작해 **임의의 전적을 서버에 보낼 수 있다.** 조작이 쉬운 리더보드는 신뢰를 잃고 빠르게 방치된다.

제대로 막으려면 서버가 기보를 재검증해야 하고, 이는 **엔진을 서버에도 배포**한다는 뜻이다. "백엔드 없음 / 서버 비용 0"이라는 프로젝트 전제([index.md](../index.md) §1)와 정면으로 충돌한다.

### 2. 사용자가 적을 때는 역효과

랭킹은 모수가 있어야 동기가 된다. 참여자가 소수인 리더보드는 **앱이 한산하다는 신호**로 읽혀 오히려 이탈을 유발한다. 랭킹은 사람이 모인 뒤 켜는 기능이다.

### 3. 계정 도입의 마찰

랭킹에는 신원이 필요하다. 로그인은 "짬날 때 잠깐 두는" 캐주얼 지향([game-modes.md](../spec/game-modes.md))과 충돌한다.

## 대안 — 먼저 할 것

랭킹 대신 **서버·계정 없이 작동하고, 사용자가 0명이어도 유효한** 경로를 우선한다.

- **데일리 퍼즐 + 결과 공유** (Wordle식): 치팅해도 남에게 자랑할 대상이 없어 무의미하고, 공유가 곧 유입 경로가 된다.
- 스트릭([streak.md](../spec/streak.md)): 자신과의 비교만으로 리텐션을 만든다.

## 재검토 조건

다음이 충족되면 다시 판단한다.

1. 꾸준한 사용자(재방문)가 리더보드가 한산해 보이지 않을 정도로 확보됨.
2. 치팅 대응 방침이 정해짐 — 서버 재검증을 감수하거나, **조작해도 무해한 지표**(예: 익명 집계 "오늘 퍼즐 상위 20%")로 한정.
3. 계정 없이 신원을 다룰 방법(익명 ID 등)이 정리됨.

도입 시 백엔드는 [001](001-cloud-sync-firebase.md)에서 채택한 Firebase Spark 플랜을 재사용한다.

## 영향

- `docs/index.md` §6의 "서버 기반 랭킹 범위 밖"은 **그대로 유지**한다.
- 스트릭은 로컬 지표로 남는다 — 기기 변경·캐시 삭제 시 초기화된다는 한계를 감수한다(클라우드 동기화는 [001](001-cloud-sync-firebase.md) 소관).
